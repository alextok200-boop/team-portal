# 团队门户（静态版）

内部权限门户的 **GitHub Pages 静态部署版**。

> 由 Node 后端版（`login-portal` v2.0.0）改造而来，去掉后端，改为**纯前端**实现，
> 以便免费托管在 GitHub Pages。

## ✨ 与后端版的差异

| 能力 | 后端版（login-portal） | 本静态版 |
|---|---|---|
| 登录鉴权 | 服务端 scrypt 哈希 | **前端 SHA-256 哈希比对** |
| 用户/角色管理 | 服务端落盘，全员共享 | **localStorage 本地存储**（admin 后台配置仅本浏览器生效） |
| 日报数据 | 服务端每日 11:00 / 17:00 自动抓取 | **静态 JSON 快照**（GitHub Actions 抓取后推送更新） |
| 会话 | HMAC 签名令牌 | localStorage 令牌（8 小时） |
| 部署 | 需 Node 服务器 | **GitHub Pages 免费静态托管** |

> ⚠️ **静态版是「弱鉴权」**：源码可见、前端密码哈希可被绕过，仅供内部轻量使用。
> 若需要真正的服务端鉴权与共享用户管理，请用后端版（`C:\Users\alext\Web\login-portal`）。

## ⚙️ 关键实现说明

### 1. base 前缀（GitHub Pages 子路径部署）

本项目部署在 `/team-portal/` 子路径，所有资源引用采用**相对路径 + 静态 `<base>` 标签**：

- 每个 HTML `<head>` 顶部有 `<base href="/team-portal/">`
- 资源引用（`css/...`、`js/...`、`pages/...`）为相对路径，由 `<base>` 统一解析
- JS 里的跳转通过 `Site.url('/xxx')` 拼接、权限比对通过 `Site.strip()` 剥前缀

> ⚠️ **若改了仓库名，需同步修改每个 HTML 里的 `<base href="/team-portal/">`**
> 为 `/<新仓库名>/`。

> ⚠️ **`<base>` 的副作用：相对 URL 是按「站点根」解析的，不是按当前目录。**
> 所以在 `pages/` 下的页面里裸写 `tables.html`，浏览器会去请求 `/team-portal/tables.html`，
> 而真实文件在 `/team-portal/pages/tables.html` ⇒ **点一下直接 404**。
> 最坑的是这类写法静态看代码"很像是对的"：文件名没错、目标页也在、也没打错字。
>
> 规则：**页面间跳转一律走 `Site.url('pages/xxx.html')`**（`js/board.js` 里收敛成 `tableUrl()`）。
> 只有根级页面 `index.html` / `login.html` 可以裸写。
> 防复发见 `tools/smoke-site.js` 第 ⑧ 组 —— 它按站点根做基准逐文件扫，少一层 `pages/` 就红。

### 2. 登录与用户账号（前端 · 三源合并）

`js/api.js` 把原后端 `/api/*` 调用映射到本地实现。用户表由**三层合并**而成，按 `username`（忽略大小写）去重，高优先级整体覆盖低优先级：

```
①  js/config/roles.js  DEFAULT_USERS   源码内置   全站生效   （admin / leader / member）
②  data/users.json     共享名单        随仓库部署 全站生效   ← 新增用户靠它
③  localStorage        本机覆盖层      仅管理员本机
```

- 登录：`crypto.subtle.digest('SHA-256', 密码)` 与哈希比对；新哈希带 `sha256$` 前缀，同时兼容历史无前缀的裸 SHA-256
- 会话：localStorage 存令牌（8 小时过期）
- 角色/日志：localStorage 持久化（角色首次用 `roles.js` 默认值）
- `lastLogin` 单独存在 `portal_lastlogin`，**登录不再回写整张用户表** —— 否则成员浏览器会留下陈旧快照，把管理员后来在仓库里的改动盖回去
- 本机覆盖层只落「与共享名单不等价」的差异记录，等价的陈旧副本会被自动清理

#### ⚠️ 新增用户为什么必须「导出 + 提交」

GitHub Pages 是纯静态托管，**浏览器没有服务端可写**。所以在管理后台点「新增用户」，本质上只是写进了你**这台电脑的 localStorage**：

| 场景 | 结果 |
|---|---|
| 在**建号那台浏览器**里登录 | ✅ 立即可以 |
| 同事在**自己的电脑 / 别的浏览器**登录 | ❌ 报「账号或密码错误」（他的浏览器里没有这条记录） |

要让账号全站生效，二选一：

**A. 一键发布（配过 Token 之后最快，推荐）**

```
管理后台 → 自动提交 → 填一次 GitHub Token（见下方 §自动提交）
之后：[用户管理] → 一键发布到仓库        → 提交 data/users.json
     [内容管理] → 一键发布到仓库（N）    → 提交 data/content.json
```

**B. 管理后台导出（没配 Token 时的手工路）**

```
管理后台 → 用户管理 → 导出用户配置
  → 浏览器下载 users.json
  → 覆盖仓库 data/users.json
  → git add data/users.json && git commit && git push
```

A / B 两条路产出**完全一样**的格式 —— 后端共用同一份 payload 构造逻辑，不会出现两种格式。

导出的文件只含**与源码/仓库不等价**的账号（内置的 admin/leader/member 不会重复导出），哈希带 `sha256$` 前缀，删除账号会记进 `deleted` 列表以覆盖源码内置账号。

**C. 命令行（适合加号后顺手提交）**

```bash
python tools/add-user.py --user zhangsan --pass konllen2026 --name 张三 --role member
python tools/add-user.py --user zhangsan --pass newpass2026   # 改密
python tools/add-user.py --del zhangsan                       # 删除（写 deleted 墓碑）
python tools/add-user.py --list                               # 看当前名单
```

**管理后台的「来源」列**会标出每个账号来自哪里：`源码` / `仓库` / `待发布`（仅本机）。看到 `待发布` 就说明还没提交。

> ⚠️ **不要用内网 IP（`http://192.168.x.x`）访问门户**：那不是浏览器的「安全上下文」，
> `crypto.subtle` 不可用，无法校验密码。此类访问会**明确报错**而不是静默失败 ——
> 历史版本在这里会降级成 8 位 djb2 散列，结果是在内网 IP 下建的号换成 https 后**永远登不上**，
> 该降级路径已于 v1.4.0 移除。
> 例外：本机用 `http://localhost:8971` / `http://127.0.0.1:8971` 是安全上下文，可以正常登录。

#### 内容管理（同一套机制的第二个使用者）

`pages/content.html` 的列表 / 新增 / 编辑 / 删除走的是**和账号完全一样的路**，因为它俩面对同一个约束：

> 静态站没有后端。任何「后台写操作」都只写进**做这次操作的那台浏览器**的 localStorage。

所以内容也分三层（源码内置 ⊂ `data/content.json` ⊂ 本机覆盖层）：

| 层 | 位置 | 谁能看到 |
|---|---|---|
| 源码内置 | `js/api.js` 的默认值（内容为空） | 全部人 |
| 仓库清单 | `data/content.json` | 全部人（提交后） |
| 本机覆盖层 | 该浏览器的 localStorage | **只有你自己** |

列表「来源」列标 `仓库` / `待发布`；页面顶部还有一条**待发布汇总条**，本机有未发布改动时变红提示。

**发布流程**（二选一，见 §自动提交）：
- 配过 Token：内容管理页右上角「**一键发布到仓库（N）**」点一下即可；
- 没配：点「**导出内容配置**」→ 下载 `content.json` → 覆盖仓库 `data/content.json` → 提交。

同事刷新即见。

删除与账号同理：
- 删**本机新建**的条目 → 直接消失。
- 删**仓库里已有**的条目 → 单独写一条 `deleted` **墓碑**（否则下次合并会把它「还原」），导出后全站同步删除。

字段校验（`validateContent`）：标题必填且 ≤80 字；类型只能是 `文档/图片/视频/链接`；状态只能是 `草稿/已发布/已归档`；说明 ≤2000 字；链接须以 `http(s)://` 或 `/` 开头。

**权限**：读是登录即可；写（新增 / 编辑 / 删除 / 导出）仅管理员。成员打开同一页面是**只读**视图 —— 没有编辑按钮，写接口一律 403。

> 🧩 用户表与内容表共用 `js/datastore.js` 里**同一份**三源合并实现，只是喂进去的配置不同（主键、等价字段、默认值）。
> **不要把合并逻辑抄第二遍** —— 抄了必然漂移。

#### 自动提交：不用再手工 git 提交（v1.6.0）

前面两节都在说「导出文件 → 覆盖仓库 → 提交」。这一步可以省掉：**管理后台 →「自动提交」** 填一次 GitHub Token，之后加人 / 发内容点「一键发布到仓库」就直接提交。

**怎么工作的**：浏览器直接调 GitHub Contents API（`PUT /repos/{owner}/{repo}/contents/{path}`）。实测 GitHub 对带 `Authorization` 的跨域请求是放行的（预检通过），所以**纯静态站也能做到这件事，不需要任何后端**。

**Token 怎么生成**（一次性，约 1 分钟）—— 管理后台「自动提交」页签里也写了同一份步骤：

1. 打开 <https://github.com/settings/personal-access-tokens/new>
2. **Token name** 随便填，如 `team-portal 自动提交`；**Expiration** 选个有效期（如 90 天）
3. **Resource owner** 选 `alextok200-boop`
4. **Repository access** 选 **Only select repositories**，勾上 `team-portal`
5. **Permissions** → **Repository permissions** → 找到 **Contents** 选 **Read and write**
   （只给这一项即可；Metadata 会自动带上只读）
6. 点底部 **Generate token**，复制以 `github_pat_` 开头的那串 —— **只显示这一次，务必当场复制**
7. 粘回「管理后台 → 自动提交」的 Token 框，点「保存配置」

> 用 **Classic token**（`ghp_`，勾整个 `repo`）也能跑通，但它会给到**该账号下所有仓库**的读写权，
> 范围远大于所需，**不推荐**。

**「保存配置」会真的试写一次**（v1.6.3）—— 这是为了修一个真实误判：
「已配置」以前只看 `GET /repos/{owner}/{repo}`，而它有两个问题：

- 该端点**只需要 `Metadata: read`**，所以一个只勾了「元数据只读」的 Token 也能返回 200；
- 返回体里的 `permissions.push` 反映的是**你这个账号在仓库里的角色**，不是 Token 的权限 ——
  GitHub 原话是 *"A token cannot grant additional access capabilities to a user"*。
  仓库是你自己的，`push` 恒为 `true`，**跟 Token 勾了什么完全无关**。

结论：光看 `GET /repos` 把「只读 Token」误判成「可写」是必然的，要等第一次发布才炸出 403。
现在保存时会额外打一次 `POST /repos/{owner}/{repo}/git/blobs` —— GitHub 要求它必须持
**Contents: write**，而它只往对象库丢一个**游离 blob**（不产生 commit、不动分支、不触发
Pages 重建、不影响任何文件）。于是：

- 返回 `201` → 确认可写，配置存下，状态栏显示「已配置（Token 尾号 XXXX，**已确认可写**）」；
- 返回 `403` → 判定只读，**保存直接失败**并提示去把 Contents 改成 `Read and write`；
- 网络抖动 / 判定不了 → **不阻断保存**，留到真正发布时兜底报错。

> 老配置没有这个确认标记时，状态栏只显示「已配置（Token 尾号 XXXX）」—— 不显示成「只读」，
> 只是「未验证」。重新点一次「保存配置」即可补上确认。

> 🔒 **Token 只存在你这台浏览器的 localStorage**（键 `portal_gh_cfg`）——
> **不会写进仓库，也不会随 `users.json` / `content.json` 的导出泄漏**（回归脚本专门断言了这点）。
> 它是**明文**存储：公用电脑别配。怀疑泄漏就去 GitHub 撤销，回来点「清除配置」换一把新的。
> 门户仓库本身是 Public，但**任何时候都不要把 Token 提交进文件**。

**冲突处理**：提交时带上「读取时拿到的 sha」（Contents API 的乐观锁）。如果期间远端被别处改过
（比如 Actions 的定时数据提交），接口会返回 409，界面提示「请刷新后重试」——
**不会静默覆盖别人的改动**。

**发布成功后**：本地缓存的仓库内容立刻更新，列表里的「待发布」标记**当场**变「仓库」、

### 3. 日报数据（钉钉自动抓取链路）

`data/daily.json` 是钉钉 AI 表格《电商营销备战-日报追踪表》的静态快照，**全自动更新**：

```
钉钉 AI 表格 → GitHub Actions（每天 11:00 与 17:00）→ scripts/fetch-openapi.js
             → data/daily.json → 自动 commit/push → 网站自动更新
```

- 数据源 baseId：`OG9lyrgJPzYDzl1ESvXRdpEYWzN67Mw4`（共 17 张表，抓取其中 9 张）
- 定时器：`.github/workflows/fetch.yml`，**每日两次** —— UTC 03:00（北京 **11:00**）与 UTC 09:00（北京 **17:00**），另支持手动 `workflow_dispatch`
  - ⚠️ **cron 是 UTC**。中国不实行夏令时，UTC+8 恒定，所以不存在时区漂移
  - ⚠️ **别指望准点**：GitHub 明确说 `schedule` 在负载高峰会延迟，而**整点正是最拥堵的时段**（原文 *"high load times include the start of every hour"*）。实测多为 `11:0x–11:2x` / `17:0x–17:2x` 完成，偶尔可能被跳过。若哪天需要「必须准点看到」，把分钟错开到 `:50` 比整点更靠谱
- 每表行数上限：**双层设计** —— `rawCap`（扫描多少原始行，默认 **20000**，分店铺表 16000/24000）+ `keepCap`（保留多少有效行，默认 8000）
- ⚠️ **为什么要双层**：日报追踪表里预建了整年的**空白模板行**（只有日期/星期/促销节点）。单一上限会被空白行挤占，导致真数据被截断 —— 200 行上限时国内表只捞到 24 条有效记录，实际有 799 条
- 默认上限定到 20000 的依据（2026-09-10 实测）：9 张表里最长的两张（投放 / 内容）各有 **7938 行**；上限若低于表长，`truncated` 会恒为真、误报「数据可能不完整」。上限只是天花板，表短则自然扫到表尾、不额外耗时
- 空白模板行默认**丢弃**（`DINGTALK_DROP_EMPTY=0` 可保留），并在 payload 里报告 `rawRows` / `droppedEmptyRows`，丢弃不无声
- 抓取脚本带**指数退避重试**（网络抖动不再整表失败），输出 `truncated` / `emptyTables` / `failedTables` 元数据 —— **截断、空表、失败三种状态不再混淆**
- 「空表」= 整表扫完（未到上限）却零有效行，属模板表尚未录入的正常状态；看板读 `emptyTables` 自动列出，**不在前端硬编码表名**
- 所需 4 个 GitHub Secret：`DINGTALK_APP_KEY` / `DINGTALK_APP_SECRET` / `DINGTALK_OPERATOR_ID` / `DINGTALK_BASE_ID`
- 🔔 **失败了会推钉钉群**：workflow 末步 `if: failure()` → `scripts/notify-failure.js`，消息含北京时间、触发方式与**可点的运行日志链接**。
  需额外配一个 Secret：**`DINGTALK_ROBOT_WEBHOOK`**（钉钉群自定义机器人的 Webhook；安全设置选「自定义关键词」，关键词填 `日报抓取`）。
  **没配只是不发通知、不会让构建失败**（脚本会打 `::warning::` 把配置方法写进日志）。
- 👁️ **页面上能一眼看出过期**：6 处「最近同步」都带新鲜度标签（`数据正常` / `数据偏旧` / `⚠ 数据已过期`）。
  阈值依据排期推导：`17:00 → 次日 11:00 = 18h` 是正常的最长间隔，故 `< 20h` 正常、`≥ 26h` 标红。
- ⚠️ **上面两个机制是互补的，不是二选一**：通知只覆盖「跑了但失败」；`schedule` 被 GitHub 在高负载时段
  **跳过**时压根不会有 run，也就不会有通知 —— 那种情况只能靠页面标签被发现。

> ⚠️ **钉钉 OpenAPI 拿不到「公式 / 查找引用 / 关联引用 / 自动编号」字段**（官方限制）。
> 日报总览的 GMV / 订单 / UV 是公式字段，所以看板核心指标**改从「分店铺日报」聚合**
> （分店铺的 GMV / 订单 / UV 是手工录入，可以拿到）。

### 4. 本地 Git 同步（重要）
本项目的推送常需走 **Git Data API 绕行**（blob → tree → commit → ref），
因为本机 `git push` 走 github.com:443 会被 reset / SSL 中断。**API 推送不会回写本地 git**，
长期下来本地历史会与远端分叉（本地 `git log` 看不到真实版本、`git pull` 冲突、本地无法当回滚点）。

因此：**凡做过 API 推送，或不确定本地是否落后，跑一次**

```bash
bash tools/sync-local.sh            # 对齐；工作区有未提交改动则先备份并停下（不丢东西）
bash tools/sync-local.sh --check    # 只报告差多少，不动文件（落后时退出码 2）
bash tools/sync-local.sh --force    # 确认丢弃未提交改动，强制对齐
```

> 🔒 **防误删闸门**：工作区有未提交改动时，脚本会先整包备份到 `../_backup/`，
> 然后**停下并列出**将被丢弃的文件，必须显式加 `--force` 才继续。
> （这条闸门是踩坑换来的：早期版本直接 reset，把刚改好的文件无声冲掉了。）

脚本走**双通路**，因为本机 `github.com` 时通时断：

| 通路 | 触发条件 | 做法 |
|---|---|---|
| ① `git fetch` | github.com:443 可达 | 直接取回对象（首选） |
| ② `api.github.com` 兜底 | fetch 被 reset / 502 / SSL eof | `tools/fetch-remote-commit.py` 从 API 取远端 SHA，**在本地重建同 SHA 的 commit 对象**，再 reset |

另有两个环境坑已在脚本内处理：
- **代理干扰**：脚本开头 `unset http_proxy/https_proxy/...`（沙箱注入的代理常让 github.com 的 CONNECT 隧道 502）
- **`git update-ref` 静默失效**：受限环境下 git 写 `.git/refs/remotes/**` 会无声失败，导致 `origin/main` 解析不到、`git status` 永远显示 up-to-date —— 脚本用幂等直写兜底

> ⚠️ `git reset --hard` 会删掉「只在旧提交里存在」的文件（实测踩过：回退时把整个 `tools/` 目录删了）。
> 该脚本只用于**向前对齐**，不要拿它当回退工具。
>
> 正常网络下 `git push` / `git pull` 可直接用；只有 443 被中断时才需要 API 绕行。
> 无论走哪条路，推送后养成跑一次 `sync-local.sh` 的习惯。
